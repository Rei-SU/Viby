# Windows state — issues found while validating Viby on Windows

Generated by a Windows (win32/x64) pass over the project at commit `3067e0c` (0.2.1).
Scope: things that do not work, look wrong, or are unverified on Windows. macOS behaviour is the reference.

Severity: **Blocker** (prevents running/building), **Major** (feature broken or visibly wrong), **Minor** (cosmetic/ergonomic), **Unverified** (design claim not yet checked on real hardware).

---

## 1. Build & packaging

### 1.1 `npm run dist:dir` / `dist:win` fail on a standard user account — Blocker
`electron-builder` extracts its `winCodeSign` 7z archive, which contains macOS
symlinks (`darwin/10.12/lib/libcrypto.dylib`, `libssl.dylib`). Extracting those
requires the "Create symbolic links" privilege, which a normal Windows account
does not have unless Developer Mode is enabled (or the shell is elevated).

Reproduced locally:
```
ERROR: Cannot create symbolic link : A required privilege is not held by the client.
```
CI (`windows-latest`) has Developer Mode on, so published builds are fine; a
developer cloning the repo on a stock Windows install cannot produce an installer.

**Files:** `electron-builder.yml`, electron-builder's winCodeSign cache
**Fix direction:** document "enable Developer Mode" in README/TESTING, or set
`CSC_IDENTITY_AUTO_DISCOVERY=false` and avoid the code-sign toolchain; or extract
with symlink creation disabled.

### 1.2 `node_modules` is stale relative to `package.json` — Major
`package.json` requires Electron `^45.0.0`, but the installed copy is `37.10.3`
(no `npm install` has been run since the pulls). Everything in this report was
validated against Electron 37, which can mask Windows-only behaviour differences
(media session/SMTC, `titleBarOverlay`, etc.).
**Fix direction:** run `npm install` (and `npm run runtime`) before any Windows
validation; document as a required step.

### 1.3 `npm run icons` cannot run on Windows — Minor
`scripts/make-icons.py` shells out to macOS-only `iconutil` to build
`resources/icon.icns`. On Windows the script fails at the iconutil step. The
committed `icon.ico`/`icon.png` are usable, so this only blocks regenerating
icons on Windows.
**File:** `scripts/make-icons.py`

### 1.4 `npm run measure` is macOS-only — Minor
Hard-codes `dist/mac/Viby.app`, `ps`, and macOS process paths. Not runnable on
Windows.
**File:** `scripts/measure.mjs`

## 2. Window chrome (double title bar) — Major
On macOS, `titleBarStyle: 'hiddenInset'` removes the native bar and the app draws
its own 46px titlebar (drag region, back/forward, search, net pill, profile).

On Windows, `titleBarStyle: 'default'` keeps the **native** Windows caption bar
(39px, measured: `outerHeight - innerHeight = 39`), and the app *also* renders
its own 46px `.titlebar` below it. Result: two stacked title bars, wasted
vertical space, and a redundant drag strip.

Measured in the running app:
- `.titlebar` height = 46px, `webkitAppRegion: drag`
- native caption = 39px (`outerHeight 760 - innerHeight 721`)

**Files:** `src/main/windows.ts` (`titleBarStyle: isMac ? 'hiddenInset' : 'default'`),
`src/renderer/App.svelte` (`.titlebar`)

**Fix direction:** either (a) `titleBarStyle: 'hidden'` + `titleBarOverlay: true`
on Windows (keeps native min/max/close overlaid on the web titlebar — Windows 11;
needs a fallback for Windows 10), or (b) drop the custom titlebar on Windows and
keep the native caption. The current code gives the worst of both.

## 3. Runtime / yt-dlp provisioning

### 3.1 Windows runtime is not trimmed — Minor (size)
`scripts/fetch-runtime.mjs`'s `trim()` targets POSIX paths (`lib/python3.12`,
`bin/...`). On Windows the stdlib lives in `Lib/` and `DLLs/`, so every `rmSync`
for `idlelib`, `tkinter`, `ensurepip`, `pip`, `setuptools`, `tcl`, etc. is a
no-op. The vendored runtime is ~59 MB instead of the intended trimmed size, and
ships tkinter/idlelib/ensurepip/pip/setuptools/tcl that a headless audio
extractor never needs.

**File:** `scripts/fetch-runtime.mjs` (`trim`)
**Fix direction:** add a Windows branch that trims `Lib/idlelib`, `Lib/tkinter`,
`Lib/ensurepip`, `Lib/site-packages/{pip,setuptools,pkg_resources}`, and
`DLLs/tcl*`/`tcl/`.

### 3.2 Microsoft Store Python alias can hijack dev/runtime fallback — Minor
`findPython()` in `binary.ts` scans `PATH` for `python.exe`/`python3.exe` and
uses `isExecutable()` (which on Windows only checks existence). The WindowsApps
"App execution alias" stubs (`python.exe`, `python3.exe`) are 0-byte shims on
PATH that open the Microsoft Store. They pass `isExecutable()` and are tried
before the fallback list (which is empty on Windows). When the vendored runtime
is absent (fresh clone without `npm run runtime`), `works()` runs the stub,
which can pop a Microsoft Store window and return a confusing failure.

**File:** `src/main/ytdlp/binary.ts` (`findPython`, `isExecutable`)
**Fix direction:** resolve the real interpreter via `py` launcher or filter out
the WindowsApps alias path; or prefer `py.exe -3`.

### 3.3 `exec.ts` uses SIGKILL on Windows — Minor
`child.kill('SIGKILL')` is mapped by Node to `TerminateProcess` for the direct
child, but any grandchild (e.g. a spawned ffmpeg) is not killed. Also
`child.kill()` returns before the process exits. Generally fine for yt-dlp
(Python is the direct child), but worth noting for the binary fallback path.
**File:** `src/main/ytdlp/exec.ts`

## 4. UI / platform-specific code

### 4.1 Media keys / Now Playing via `navigator.mediaSession` — Unverified
The player relies entirely on `navigator.mediaSession` for OS media keys and the
Now Playing panel on both platforms. On Windows this maps to SMTC, which needs a
packaged app with a proper AppUserModelID to show artwork/title in the taskbar
overlay. In dev (and possibly in unsigned builds) media keys may not register.
Also no `globalShortcut` fallback exists.

**File:** `src/renderer/lib/player.svelte.ts` (`setMediaHandlers`)
**Fix direction:** manual test on a packaged build; consider registering
`MediaPlayPause`/`MediaNextTrack`/`MediaPreviousTrack` global shortcuts as a
fallback on Windows.

### 4.2 `menu.ts` removes all menus on Windows — Minor
`Menu.setApplicationMenu(null)` on Windows removes Ctrl+C/V/X/A/Z accelerators
from the default menu. Chromium handles them in inputs, but there is no DevTools
shortcut (Ctrl+Shift+I) in dev on Windows because the View menu is gone. Dev
ergonomics only.
**File:** `src/main/menu.ts`

### 4.3 Modifier-key handling is fine
`Ctrl+K` is handled (`event.metaKey || event.ctrlKey`) and the shortcut hint
shows `Ctrl K`. No change needed.
**File:** `src/renderer/components/SearchBar.svelte`

## 5. File system / paths

### 5.1 `json-store.ts` writes `file.tmp` beside the data file — OK but fragile
Atomic write uses `${file}.tmp` + `renameSync`. On Windows, renaming over an
existing file works (Node maps to replace-existing). No issue observed. `mkdirSync(join(file, '..'))` relies on `join` normalising `..`, which it does.
**File:** `src/main/json-store.ts`

### 5.2 `mediaUrlFor` / `pathFromMediaUrl` round-trip — OK
Windows drive paths (`C:\...`) are encoded in the URL and decoded back. The
protocol handler's allowed-root check uses `sep` correctly. No issue observed.
**Files:** `src/main/media.ts`, `src/main/ipc.ts` (`handleMediaProtocol`)

### 5.3 Downloads manager's `finalPath` detection — OK
The regex `/^([A-Za-z]:\\|\/)/` handles Windows drive letters. `--print
after_move:filepath` output is split on `\n` with `\r` stripped. No issue.
**File:** `src/main/downloads/manager.ts`

### 5.4 Downloads store uses forward-slash `join` for art paths — Minor
`artNameFor` returns `join('art', name)` which on Windows is `art\name`. Stored
in `index.json` as a backslash path. Cross-platform portability of a saved
library is not a goal, but a user moving `%APPDATA%\Viby` between machines
would break artwork. Not Windows-specific per se.
**File:** `src/main/downloads/store.ts`

## 6. Updates (Windows-specific path)

### 6.1 In-place update is a design claim, not verified — Unverified
The state machine is unit-tested with fakes; NSIS replacing a running per-user
install needs the manual smoke test in TESTING.md. `autoUpdater.quitAndInstall(false, true)`
and the `latest.yml`/manifest verification flow are untested on real hardware.
**Files:** `src/main/updater-native.ts`, `src/main/updater.ts`

### 6.2 `releaseFromGithub` selects macOS DMGs only — OK for Windows
On Windows, `fetchLatestRelease` is used for manifest verification; `installerUrl`
is undefined but the Windows path uses `native.check()`/`download()`. The
`artifacts['Viby-windows-x64.exe']` lookup matches electron-builder's
`artifactName`. No issue.
**Files:** `src/main/release-feed.ts`, `src/main/updater-native.ts`

### 6.3 `updater.log` path — OK
`app.getPath('logs')` resolves to `%APPDATA%\Viby\logs` on Windows, matching
TESTING.md.
**File:** `src/main/updater-native.ts`

## 7. Developer tooling / tests

### 7.1 `tests/unit.mjs` output path is POSIX-only — Blocker (dev)
The runner writes bundles to `/tmp/viby-<suite>.mjs`. On Windows, esbuild
resolves `/tmp/...` to `<cwd>\tmp\...` while Node resolves it to `C:\tmp\...`,
so every suite fails with `MODULE_NOT_FOUND` before running. The suites
themselves pass once the bundle path is corrected (verified by bundling into
`tests_tmp/`).

**File:** `tests/unit.mjs` (line `const out = '/tmp/viby-${name}.mjs'`)
**Fix direction:** use `os.tmpdir()` or a relative path consistently.

### 7.2 `tests/electron-stub.ts` hardcodes a macOS userData path — Minor
`getPath('userData')` returns `~/Library/Application Support/viby` on every
platform. On Windows this creates a stray `C:\Users\<u>\Library\...` directory
and bypasses Windows path semantics in the resolver/downloads tests. The
bundled Python is still found via `getAppPath()` (cwd), so tests pass, but the
path is misleading.

**File:** `tests/electron-stub.ts`
**Fix direction:** branch on `process.platform`.

### 7.3 `updates` and `release-notes` suites self-trigger their scripts' CLI — Minor
Both suites import from `scripts/update-manifest.mjs` and
`scripts/check-release-notes.mjs`, whose bottom guards
`if (import.meta.url === pathToFileURL(process.argv[1]).href) main()` become
true when the test is bundled and run as the entry module. `main()` then exits
with code 1 ("Usage: ..."). These suites cannot pass through the bundled runner
as-is.

**Files:** `scripts/update-manifest.mjs`, `scripts/check-release-notes.mjs`,
`tests/updates.test.ts`, `tests/release-notes.test.ts`
**Fix direction:** guard with an additional condition (e.g. the entry file name
ends with the script name, or check `process.env.VIBY_TEST`).

### 7.4 E2E harness uses POSIX env syntax — Minor
Docs and scripts use `VIBY_DEBUG_PORT=9222 npm run dev`, which is invalid in
PowerShell/cmd. Windows developers need `$env:VIBY_DEBUG_PORT='9222'` or a
`.env`/cross-env approach.
**Files:** `TESTING.md`, `tests/cdp.mjs`, `tests/e2e/run.mjs`

### 7.5 Single-instance lock blocks dev when an installed Viby is running — Minor
`app.requestSingleInstanceLock()` keys on userData. Running a dev build while the
installed app is open makes the dev instance quit immediately ("DevTools
listening" then exit). Work around with `--user-data-dir=<temp>`.
**File:** `src/main/index.ts`

## 8. Verified working on Windows

- `npm run build` (electron-vite) — clean.
- `npm run typecheck` — 0 errors, 0 warnings.
- `npm run runtime` (fetch + extract CPython 3.12.15) — works via System32 `tar`.
- Vendored Python runs yt-dlp (`2026.08.19`).
- Unit suites (16/19) pass once the bundle path is corrected; the 3 failures are
  harness issues above, not product bugs (plus one network-speed flake:
  "cold resolve is fast enough to stream — 14349ms (target < 8000ms)").
- App launches and renders (headless capture): titlebar, icon rail, search
  shortcut (`Ctrl K`), platform `Win32` all correct.
- `mediaUrlFor` / protocol handler path handling round-trips Windows paths.
- Downloads manager's `finalPath` detection handles drive letters.

## 9. Not covered by this pass

- In-place NSIS update (manual smoke test).
- Windows 10 (only Windows 11 was available).
- Installer signature/notarisation (not applicable to Windows).
