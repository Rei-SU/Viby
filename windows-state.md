# Windows state — issues found while validating Viby on Windows

Generated by a Windows (win32/x64) pass over the project at commit `3067e0c` (0.2.1).
Branch status updated for `windows-fixes` on 2026-10-24; Windows 11 manual checks
on Electron 37 included the offline/download flow and in-client updates.
The Electron 45 re-check was completed on Windows 11 on 2026-10-25. Windows 10 is
covered by the same x64 build and the same validation; the maintainer closed the
separate hardware pass by decision.
Scope: things that do not work, look wrong, or are unverified on Windows. macOS behaviour is the reference.

Severity: **Blocker** (prevents running/building), **Major** (feature broken or visibly wrong), **Minor** (cosmetic/ergonomic), **Unverified** (design claim not yet checked on real hardware).

---

## 1. Build & packaging

### 1.1 `npm run dist:dir` / `dist:win` fail on a standard user account — Blocker
`electron-builder` extracts its `winCodeSign` 7z archive, which contains macOS
symlinks (`darwin/10.12/lib/libcrypto.dylib`, `libssl.dylib`). Extracting those
requires the "Create symbolic links" privilege, which a normal Windows account
does not have unless Developer Mode is enabled (or the shell is elevated).

Reproduced locally:
```
ERROR: Cannot create symbolic link : A required privilege is not held by the client.
```
CI (`windows-latest`) has Developer Mode on, so published builds are fine; a
developer cloning the repo on a stock Windows install cannot produce an installer.

**Files:** `electron-builder.yml`, electron-builder's winCodeSign cache
**Fix direction:** document "enable Developer Mode" in README/TESTING, or set
`CSC_IDENTITY_AUTO_DISCOVERY=false` and avoid the code-sign toolchain; or extract
with symlink creation disabled.

**Status:** Documented in `57d3c60` — `TESTING.md` now calls out Developer Mode
for local Windows packaging. The underlying electron-builder extraction still
requires Developer Mode or elevation.

### 1.2 `node_modules` was stale relative to `package.json` — Closed
`package.json` requires Electron `^45.0.0`, but the original pass used the
installed copy at `37.10.3`. That could mask Windows-only behaviour differences
(media session/SMTC, `titleBarOverlay`, etc.).
**Fix direction:** run `npm install` (and `npm run runtime`) before any Windows
validation; document as a required step.

**Status:** Closed. Electron 45 was installed on the Windows 11 machine and the
§9 checks were repeated successfully on 2026-10-25 (§11). Windows 10 uses the
same x64 build; the maintainer accepted the Windows 11 pass as representative.

### 1.3 `npm run icons` cannot run on Windows — Closed
`scripts/make-icons.py` shells out to macOS-only `iconutil` to build
`resources/icon.icns`. On Windows the script failed at the iconutil step. The
committed `icon.ico`/`icon.png` are usable, so this only blocked regenerating
icons on Windows.
**File:** `scripts/make-icons.py`

**Status:** Closed. `iconutil` is now optional (the existing `.icns` is kept when
it is missing), and `npm run icons` runs `scripts/make-icons.mjs`, which finds
whichever of `python`/`py`/`python3` exists. Verified on Windows 11 with Python
3 + Pillow.

### 1.4 `npm run measure` is macOS-only — Minor
Hard-codes `dist/mac/Viby.app`, `ps`, and macOS process paths. Not runnable on
Windows.
**File:** `scripts/measure.mjs`

## 2. Window chrome (double title bar) — Major
On macOS, `titleBarStyle: 'hiddenInset'` removes the native bar and the app draws
its own 46px titlebar (drag region, back/forward, search, net pill, profile).

On Windows, `titleBarStyle: 'default'` keeps the **native** Windows caption bar
(39px, measured: `outerHeight - innerHeight = 39`), and the app *also* renders
its own 46px `.titlebar` below it. Result: two stacked title bars, wasted
vertical space, and a redundant drag strip.

Measured in the running app:
- `.titlebar` height = 46px, `webkitAppRegion: drag`
- native caption = 39px (`outerHeight 760 - innerHeight 721`)

**Files:** `src/main/windows.ts` (`titleBarStyle: isMac ? 'hiddenInset' : 'default'`),
`src/renderer/App.svelte` (`.titlebar`)

**Status:** Fixed in commit `26be262` and verified on Windows 11 (Electron 45) —
window drags correctly, overlay buttons present, no native caption remaining.
Windows 10 uses the same x64 build; no separate hardware pass is planned.

**Implementation:** `titleBarStyle: 'hidden'` + `titleBarOverlay` on Windows.

## 3. Runtime / yt-dlp provisioning

### 3.1 Windows runtime is not trimmed — Minor (size)
`scripts/fetch-runtime.mjs`'s `trim()` targets POSIX paths (`lib/python3.12`,
`bin/...`). On Windows the stdlib lives in `Lib/` and `DLLs/`, so every `rmSync`
for `idlelib`, `tkinter`, `ensurepip`, `pip`, `setuptools`, `tcl`, etc. is a
no-op. The vendored runtime is ~59 MB instead of the intended trimmed size, and
ships tkinter/idlelib/ensurepip/pip/setuptools/tcl that a headless audio
extractor never needs.

**File:** `scripts/fetch-runtime.mjs` (`trim`)
**Fix direction:** add a Windows branch that trims `Lib/idlelib`, `Lib/tkinter`,
`Lib/ensurepip`, `Lib/site-packages/{pip,setuptools,pkg_resources}`, and
`DLLs/tcl*`/`tcl/`.

**Status:** Fixed in `5396a82`; the Windows branch trims `Lib/`, `DLLs/` and Tcl,
and the trimmed runtime still runs yt-dlp.

### 3.2 Microsoft Store Python alias can hijack dev/runtime fallback — Minor
`findPython()` in `binary.ts` scans `PATH` for `python.exe`/`python3.exe` and
uses `isExecutable()` (which on Windows only checks existence). The WindowsApps
"App execution alias" stubs (`python.exe`, `python3.exe`) are 0-byte shims on
PATH that open the Microsoft Store. They pass `isExecutable()` and are tried
before the fallback list (which is empty on Windows). When the vendored runtime
is absent (fresh clone without `npm run runtime`), `works()` runs the stub,
which can pop a Microsoft Store window and return a confusing failure.

**File:** `src/main/ytdlp/binary.ts` (`findPython`, `isExecutable`)
**Fix direction:** resolve the real interpreter via `py` launcher or filter out
the WindowsApps alias path; or prefer `py.exe -3`.

**Status:** Fixed in `f6ce6f5`; `findPython` prefers `py.exe -3` and skips the
Microsoft Store aliases before scanning `PATH`.

### 3.3 `exec.ts` uses SIGKILL on Windows — Minor
`child.kill('SIGKILL')` is mapped by Node to `TerminateProcess` for the direct
child, but any grandchild (e.g. a spawned ffmpeg) is not killed. Also
`child.kill()` returns before the process exits. Generally fine for yt-dlp
(Python is the direct child), but worth noting for the binary fallback path.
**File:** `src/main/ytdlp/exec.ts`

### 4.3 Modifier-key handling is fine
`Ctrl+K` is handled (`event.metaKey || event.ctrlKey`) and the shortcut hint
shows `Ctrl K`. No change needed.
**File:** `src/renderer/components/SearchBar.svelte`

### 4.4 Taskbar thumbnail toolbar (hover preview) — Verified
The preview shown when hovering the taskbar button had no playback controls.
Implemented with `BrowserWindow.setThumbarButtons`: previous / play-pause / next,
theme-aware 32px PNGs (`resources/thumbar/{dark,light}`), state mirrored from the
renderer over `player:taskbar` and commands returned over `player:command`.

Two Windows/Electron traps, both found the hard way:

- **`flags: ['enabled']` makes the whole call fail.** Electron maps it to
  `THB_FLAGS` with an all-zero `dwFlags`; Windows then rejects the toolbar and
  `setThumbarButtons` returns `false` with no error. Enabled is the default, so
  only `['disabled']` is ever passed (`src/main/taskbar.ts`, `thumbarButton`).
- **The first call must wait for the window to be visible.** The renderer sends
  its first state before `ready-to-show`; a hidden window has no taskbar button
  yet and the call also returns `false`.

Verified on Windows 11 (Electron 45, dev build): hover shows the three buttons,
clicking play/pause toggles playback and the button redraws as pause/play.

**Files:** `src/main/taskbar.ts`, `src/shared/ipc.ts`, `src/preload/index.ts`,
`src/renderer/lib/player.svelte.ts`, `scripts/make-icons.py`

### 4.5 Mouse side buttons (Back / Forward) — Verified on Windows
The Back/Forward buttons on a mouse did nothing. Viby's history is pure Svelte
state (`nav.svelte.ts`), so Chromium's own history walk is a no-op and
`webContents.goBack()` is not an option: the app never pushes a history entry.

- **Windows: the renderer sees the buttons.** An XBUTTON press arrives as
  `pointerdown` / `mousedown` / `pointerup` / `mouseup` with `button: 3` (Back,
  `buttons: 8`) or `button: 4` (Forward, `buttons: 16`), followed by `auxclick`.
  `App.svelte` handles `mouseup` only — listening to `auxclick` as well would
  step twice per press — and `preventDefault()`s it. Verified by injecting
  XBUTTON1/XBUTTON2 with `mouse_event` and logging the events.
- **`app-command` does not fire for a real XBUTTON press.** Chromium consumes
  WM_XBUTTONUP and converts it to the mouse event above. The `browser-backward` /
  `browser-forward` handler in `windows.ts` still earns its place for drivers
  that report through WM_APPCOMMAND instead (verified end to end by sending
  WM_APPCOMMAND directly), but it and the `mouseup` path can never double-step
  on a normal press. A 200ms guard in `navigate()` covers setups where both do
  fire; verified by delivering both signals 20ms apart and getting one step.
- **macOS needs the swipe relay.** Plain buttons 4/5 are swallowed by Chromium
  (which walks the single-entry history), and Logitech Options+ /
  SensibleSideButtons turn the buttons into an AppKit swipe, which Electron only
  surfaces as the macOS-only `swipe` event. `windows.ts` relays it over
  `app:navigate`. Electron names the direction after the gesture's `deltaX`, so
  `left` is Back (the mapping Chrome uses). Unverified on real hardware — no Mac
  in this pass.

Verified on Windows 11 (Electron 45, dev build): one press per history step in
both directions, a press with an empty stack is a no-op, and the titlebar arrows
enable/disable in step with the buttons.

**Files:** `src/renderer/App.svelte`, `src/main/windows.ts`, `src/shared/ipc.ts`,
`src/preload/index.ts`

### 4.6 Mouse wheel over the volume control — Verified
The volume slider ignored the wheel. Chromium has no native wheel behaviour for
`<input type="range">` and the app had no listener, so hovering it and scrolling
did nothing. `PlayerBar.svelte` now accumulates `deltaY` and spends it in whole
percent steps, 20px per point.

- **A Windows notch is 100px, `deltaMode: 0`.** Measured with real
  `WM_MOUSEWHEEL` input: one notch is exactly one `wheel` event with
  `deltaY: 100`, targeted at the input, and nothing scrolls — the player bar
  sits outside the scrolling area. 100px therefore maps to 5%.
- **`preventDefault()` only works with the listener on an element.** Chromium
  makes `wheel` passive by default on `window`/`document`/`body`; the handler
  sits on a wrapper around the slider, so the call is honoured (verified:
  `defaultPrevented` is true by the time the event reaches `window`).
- **The hit area matters more than the maths.** The track is 4px tall, so the
  slider is wrapped in an 8px-padded band (24px tall) that also reveals the
  thumb on hover.
- **Trackpads need the accumulator.** They send a stream of 1–20px deltas;
  accumulating at 20px per percent gives the same 5% per notch instead of the
  jump a 1:1 pixel mapping would cause. The accumulator resets on
  `pointerleave` so a partial step cannot leak into the next gesture.
- **Scrolling down while muted is ignored.** Muting does not clear the stored
  volume, so lowering it from a muted state would silently change what plays
  after unmuting — the gesture looks like it does nothing, so it should do
  nothing. A raise still unmutes (that is `setVolume`'s existing behaviour) and
  leaves the hint showing the new level.

Verified on Windows 11 (Electron 45, dev build): one notch moves 5% in both
directions, clamping at 0 and 100 holds, a muted player unmutes on a raise,
a down-scroll while muted leaves both the volume and the muted flag alone, and
the percentage hint shows for 800ms then fades.

**Files:** `src/renderer/components/PlayerBar.svelte`

## 5. File system / paths

### 5.1 `json-store.ts` writes `file.tmp` beside the data file — OK but fragile
Atomic write uses `${file}.tmp` + `renameSync`. On Windows, renaming over an
existing file works (Node maps to replace-existing). No issue observed. `mkdirSync(join(file, '..'))` relies on `join` normalising `..`, which it does.
**File:** `src/main/json-store.ts`

### 5.2 `mediaUrlFor` / `pathFromMediaUrl` round-trip — OK
Windows drive paths (`C:\...`) are encoded in the URL and decoded back. The
protocol handler's allowed-root check uses `sep` correctly. No issue observed.
**Files:** `src/main/media.ts`, `src/main/ipc.ts` (`handleMediaProtocol`)

### 5.3 Downloads manager's `finalPath` detection — OK
The regex `/^([A-Za-z]:\\|\/)/` handles Windows drive letters. `--print
after_move:filepath` output is split on `\n` with `\r` stripped. No issue.
**File:** `src/main/downloads/manager.ts`

### 5.4 Downloads store uses forward-slash `join` for art paths — Minor
`artNameFor` returns `join('art', name)` which on Windows is `art\name`. Stored
in `index.json` as a backslash path. Cross-platform portability of a saved
library is not a goal, but a user moving `%APPDATA%\Viby` between machines
would break artwork. Not Windows-specific per se.
**File:** `src/main/downloads/store.ts`

## 7. Developer tooling / tests

### 7.1 `tests/unit.mjs` output path is POSIX-only — Blocker (dev)
The runner writes bundles to `/tmp/viby-<suite>.mjs`. On Windows, esbuild
resolves `/tmp/...` to `<cwd>\tmp\...` while Node resolves it to `C:\tmp\...`,
so every suite fails with `MODULE_NOT_FOUND` before running. The suites
themselves pass once the bundle path is corrected (verified by bundling into
`tests_tmp/`).

**File:** `tests/unit.mjs` (line `const out = '/tmp/viby-${name}.mjs'`)
**Fix direction:** use `os.tmpdir()` or a relative path consistently.

**Status:** Fixed in `99de301` and `b7718f0`; bundles go to `os.tmpdir()`, and
the runner executes the native esbuild binary on macOS/Linux and the Node shim
on Windows.

### 7.2 `tests/electron-stub.ts` hardcodes a macOS userData path — Minor
`getPath('userData')` returns `~/Library/Application Support/viby` on every
platform. On Windows this creates a stray `C:\Users\<u>\Library\...` directory
and bypasses Windows path semantics in the resolver/downloads tests. The
bundled Python is still found via `getAppPath()` (cwd), so tests pass, but the
path is misleading.

**File:** `tests/electron-stub.ts`
**Fix direction:** branch on `process.platform`.

**Status:** Fixed in `99de301` and `b7718f0`; the stub returns the platform's
development `userData` path and keeps the directory lowercase on every platform,
matching `index.ts`'s pre-`setName` pin.

### 7.3 `updates` and `release-notes` suites self-trigger their scripts' CLI — Minor
Both suites import from `scripts/update-manifest.mjs` and
`scripts/check-release-notes.mjs`, whose bottom guards
`if (import.meta.url === pathToFileURL(process.argv[1]).href) main()` become
true when the test is bundled and run as the entry module. `main()` then exits
with code 1 ("Usage: ..."). These suites cannot pass through the bundled runner
as-is.

**Files:** `scripts/update-manifest.mjs`, `scripts/check-release-notes.mjs`,
`tests/updates.test.ts`, `tests/release-notes.test.ts`
**Fix direction:** guard with an additional condition (e.g. the entry file name
ends with the script name, or check `process.env.VIBY_TEST`).

**Status:** Fixed in `99de301`; both CLI guards also require the entry filename
to match the script, so bundled test imports no longer trigger `main()`.

### 7.4 E2E harness uses POSIX env syntax — Minor
Docs and scripts use `VIBY_DEBUG_PORT=9222 npm run dev`, which is invalid in
PowerShell/cmd. Windows developers need `$env:VIBY_DEBUG_PORT='9222'` or a
`.env`/cross-env approach.
**Files:** `TESTING.md`, `tests/cdp.mjs`, `tests/e2e/run.mjs`

**Status:** Fixed in `57d3c60`; `TESTING.md` documents PowerShell environment
syntax and the E2E command block now shows both POSIX and PowerShell forms.

### 7.5 Single-instance lock blocks dev when an installed Viby is running — Minor
`app.requestSingleInstanceLock()` keys on userData. Running a dev build while the
installed app is open makes the dev instance quit immediately ("DevTools
listening" then exit). Work around with `--user-data-dir=<temp>`.
**File:** `src/main/index.ts`

## 12. Downloaded album showed "Unknown artist" and had no lyrics (0.2.1)

Found while testing a downloaded album (*Hard To Imagine The Neighbourhood Ever
Changing*, 21 songs) on Windows. Every row and the player showed "Unknown
artist", and only 5 of 21 songs had lyrics on disk.

**Cause:** an album page keeps the artist in the header's `straplineTextOne`
(the line above the title); its subtitle is only `Album - 2021`, and the track
rows carry no artist of their own. An album opened from Home, a track's album
link or history therefore stored each row as "Unknown artist". Downloads saved
that snapshot. LRCLIB's `artist_name` filter is strict, so "Unknown artist"
returned no results and the miss was cached for 24 hours. Title-only fallback
matching also pinned wrong lyrics for the five songs fetched during the
download ("Dust" matched *Another One Bites the Dust*).

**Fix (ed790c3):**
- `extractHeader` reads the strapline for album/single/EP/compilation headers
  (playlist owners are still ignored); `toTrack` no longer uses a duration or
  play count as an artist name.
- `DownloadManager.repairCredits()` runs at startup and when the connection
  returns: it fills `artist`/`artistId`/`album` from the album page, drops
  lyrics that were looked up without a usable artist, then backfills them.
- Lyrics lookup ignores `Unknown artist`/`Various Artists` and rejects results
  credited to a different artist.

**Verified live on Windows 11:** all 21 entries now read "The Neighbourhood" and
the album name; 21/21 have correct synced lyrics (checked against LRCLIB), the
Downloads page, player and offline lyrics panel all show the right artist and
text. Existing libraries are repaired in place; nothing is re-downloaded.

Also fixed while testing (ace9512): downloaded covers are on the `viby-media:`
scheme, which the media session rejects, so Now Playing/SMTC lost the artwork
for offline songs. Main now returns the cover as a data URL
(`images:data-url`), and streaming artwork still uses the original https URL.

## 13. Artist pages showed only ten releases (0.2.2)

Found on Windows while checking Pause's artist page: his single *Sociopath*
(2022) was playable from search and history but absent from his discography,
which stopped at ten singles.

**Cause:** YouTube Music previews an artist's Albums and Singles & EPs with ten
cards and puts the complete list behind each shelf's `moreContentButton`
(`browseId=MPAD…`, page type `MUSIC_PAGE_TYPE_ARTIST_DISCOGRAPHY`). Viby only
followed global continuation tokens, and the artist response has none, so the
preview was treated as the whole discography. Pause's preview contained ten of
his 44 releases; the rest were never requested. This was platform-neutral, not
a Windows rendering issue.

**Fix:** `extractShelves` now keeps each shelf's `more` endpoint. `browse()`
follows only endpoints whose page type is `MUSIC_PAGE_TYPE_ARTIST_DISCOGRAPHY`
(Videos and Live performances use the same button but lead elsewhere), fetches
Albums and Singles & EPs in parallel, and merges the complete list by item id.
A failed "More" request keeps the ten-card preview instead of failing the page.

Discography pages themselves stop at 100 releases (Gucci Mane has 136 albums
and 137 singles & EPs). Those continuations also need the `visitorData` from
the page that produced them; without it YouTube answers "Something went wrong".
`call()` now remembers the visitor id and `discographyItems()` follows the
continuation pages, so the cap is gone as well as the ten-card preview.

**Verified live on Windows 11:** Pause's page now reports "1 albums · 44 singles
& EPs"; the Singles & EPs rail shows all 44 cards, including
`Sociopath — Single • 2022`. Albums still opens its one release (112), Daft Punk
expands to 11 albums and 26 singles & EPs, Gucci Mane reaches 136 albums and
137 singles & EPs, and the full unit suite passes.

## 14. Releases listed a song twice, as audio and as music video (0.2.2)

Some release pages list the same recording twice: the official audio track and
its music video. The Weeknd's *São Paulo* EP showed "São Paulo" at 2:29 (audio)
and again at 5:02 (video), plus a live video. The player already prefers the
official audio when a video row is played, so the second row always became the
same song.

**Fix:** `dedupeTracks()` in `src/main/innertube/parse.ts` drops a video/upload
row only when an audio row with the same normalized title exists in the same
list. Version words survive (`(Live)`, `(Remix)`, `(Acoustic)`,
`(Single Version)`), video-only tracks stay, and repeated video ids are kept
once. It runs on release track lists (`header.releaseType` present) and on an
artist's Top songs. Release cards are never deduped by title — Daft Punk really
does have five "Human After All" singles — and playlists keep their exact
contents.

**Verified live on Windows 11:** *São Paulo* now shows 3 tracks (audio, live
video, acapella) instead of 4; *After Hours* still shows all 14 album tracks;
the `navigation` and `home` e2e suites pass.
